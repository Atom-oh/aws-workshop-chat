# Workshop Chat & Q&A App — 구현 스펙

> 이 문서는 Claude Code에 그대로 전달하기 위한 구현 지시서다.
> 읽는 주체는 사람이 아니라 에이전트라고 가정하고 작성되었다.
> 애매한 부분은 추측하지 말고 **§12 질문 규칙**을 따른다.
>
> **이 문서는 v1 기준선이다.** 실제 구현은 사용자 승인을 거쳐 이 기준선에서 의도적으로 벗어난
> 부분이 있다 — 예: §5(중앙 poller/SSM push)는 구현 범위에서 제외되고 `docs/ssm-integration.md`로
> 이동, §7.1(AppSync Events)은 in-process WebSocket 허브로 대체. 이런 이탈은 README와
> `docs/`의 다른 문서에서 근거와 함께 설명된다. 이 파일 자체는 수정하지 않고 원문 그대로 보존한다.

---

## 1. 한 줄 요약

AWS 워크샵(참가자 10~500명, 기간 3일)에서 참가자 Q&A와 커뮤니케이션을 담당하는
**단일 계정 배포형 웹 채팅/Q&A 앱**을 만든다.
Slack 초대·채널 관리 노동을 제거하고, 워크샵 종료 시 **엑셀 1개 파일**을 산출한다.

---

## 2. 왜 만드는가 (문제 정의)

기존에는 Slack 무료 워크스페이스로 워크샵을 운영했고 다음 문제가 있었다.

1. 100명 규모 이메일 초대가 스팸 방어에 막힘 → 채널에 사용자를 한 명씩 수동 추가해야 했음
2. 워크샵을 회차로 반복하니 **이전 회차 사용자와 신규 사용자를 분리할 수 없음**
3. 수십 명 규모에서 질문이 스크롤에 묻혀 운영자가 미해결 질문을 추적 못 함

→ 따라서 이 앱의 성공 기준은 "채팅이 예쁘다"가 아니라
**(a) 참가자 참여에 운영자 수작업이 0회, (b) 미해결 질문이 절대 묻히지 않음, (c) 회차 데이터가 섞이지 않음** 이다.

---

## 3. 배포·수명 제약 (설계의 근간 — 절대 위반 금지)

| 항목 | 내용 |
|---|---|
| 배포 위치 | 워크샵 **Central Account** (운영자에게만 배포되는 계정) |
| 수명 | **3일. 이후 계정 자체가 삭제된다.** |
| 상주 인프라 | **없음.** 계정 밖에 상주하는 리소스/DB/S3를 전제하지 말 것 |
| 회차 개념 | 1 배포 = 1 회차. `cohortId` 같은 멀티테넌시 파티션 **불필요** |
| 참가자 계정 | 워크샵 플랫폼이 팀별 임시 AWS 계정을 벤딩. Central은 각 팀 계정에 AssumeRole 가능 |
| 산출물 | 계정 소멸 전에 다운로드된 **xlsx 1개**. 이것이 유일한 영구 자산 |
| 배포 대상 | 오준석 개인용이 아니라 **글로벌 SA들이 그대로 재사용하는 배포물** |

### 3.1 여기서 파생되는 강제 조건

- **리전 하드코딩 금지.** 참가자 지역에 가까운 리전에 배포된다. Bedrock 모델 ID도 파라미터.
- **개인정보 수집 금지.** 실명·이메일을 저장하지 않는다. 신원은 **AWS 계정 ID / 팀 번호(pseudonym)** 뿐이다.
- **내보내기를 사람 손에 맡기지 않는다.** (§8 참조) 계정 회수는 예고 없이 당겨질 수 있다.

## 4. 사용자와 신원

### 4.1 역할

| 역할 | 수 | 신원 | 권한 |
|---|---|---|---|
| 참가자 | 10~500 | 배정받은 AWS 계정 ID (또는 팀 번호) | 발언, 질문, 업보트, 파일 업로드, AI 챗 |
| 운영자 | 1~5 | 표시명 고정 `운영자` | 위 전부 + 해결 토글, 채널 생성/아카이브, 랩 스텝 변경, 메시지 삭제, 내보내기 |

### 4.2 익명성 정의 (그대로 UI에 반영)

- 참가자끼리는 **서로 익명**이다. 화면 표시는 `참가자 ...7391` 형태(계정 ID 뒤 4자리) 또는 팀 번호.
- **운영자는 전체 계정 ID를 볼 수 있다.**
- 로그인 화면에 다음 문장을 반드시 노출한다:
  > 참가자 간에는 익명입니다. 운영자는 참가자의 AWS 계정 ID를 확인할 수 있습니다.
- 아카이브(엑셀)에는 계정 ID까지만 남는다. 계정↔실명 매핑은 이 앱이 다루지 않는다.

## 5. 참가자 참여 경로 (가장 중요한 요구사항)

**목표: 참가자 타이핑 0회. 링크 클릭 한 번.**
비밀번호를 사람이 옮겨 적는 설계는 500명 규모에서 반드시 실패한다.

### 5.1 신원 등록: 중앙 생성 → 하위 push (방향 주의)

비밀번호는 **중앙이 생성해서 팀 계정으로 내려보낸다.** 팀 스택이 생성해서 중앙이 read-back 하는 반대 방향은 채택하지 않는다.
(이유: 변경 감지 로직, 크로스어카운트 KMS 복호화 읽기, 진실 원천 이중화가 모두 사라진다.)

```
[중앙 poller]  팀 계정 목록 확인 (Organizations ListAccounts 또는 파라미터로 주입된 계정 목록)
            → Cognito에 미등록인 계정 발견
            → 랜덤 크리덴셜 생성
            → AdminCreateUser + AdminSetUserPassword(permanent)   ※ FORCE_CHANGE_PASSWORD 플로우 회피
            → 해당 팀 계정에 AssumeRole → SSM PutParameter (SecureString)
                 /workshop/chat/credentials
[팀 CFN]     이 앱과 관련해 아무것도 하지 않는다
```

- **멱등성 필수.** 상태 비교는 "Cognito에 이 username이 있는가" 한 줄로 끝나야 한다.
- username = 팀 번호 또는 계정 ID (배포 파라미터로 선택).

### 5.2 하이브리드: push + reconcile

- **푸시 경로(선택):** 팀 CFN Custom Resource가 중앙 등록 API를 직접 호출 → 지연 0.
  실패해도 팀 스택은 이를 무시한다(`ShouldFail=false` 취급).
- **리컨실 경로(필수):** poller가 **2분 틱**으로 누락분만 메꾼다. 30초는 불필요하게 짧다.
- 늦게 벤딩되는 팀도 자동 합류해야 한다. CFN 간 직접 의존은 금지.

### 5.3 poller 구현 요구사항

- **계정별 병렬화 필수.** 순차 처리는 500계정에서 한 바퀴가 수 분~수십 분이 된다.
  Step Functions Map(동시성 20~30) 또는 Lambda fan-out 중 하나를 선택하고 이유를 README에 남긴다.
- `AdminCreateUser` 스로틀링 대비 **지수 백오프 + 다음 틱 재시도.** 멱등이므로 자연 복구된다.
- CloudWatch 메트릭 **1개**를 반드시 publish: `RegisteredTeams / DiscoveredAccounts`.
  운영자가 워크샵 시작 전에 보는 유일한 숫자다.

### 5.4 참가자 측 조인 스크립트 (전원에게 동일한 SSM 문서 1회 브로드캐스트)

```bash
CRED=$(aws ssm get-parameter --name /workshop/chat/credentials \
       --with-decryption --query Parameter.Value --output text)
JOIN="https://<cf-domain>/j?t=$(printf '%s' "$CRED" | base64 | tr -d '\n')"
echo "채팅 참여: $JOIN" | tee ~/JOIN_CHAT.txt
```

- 터미널 출력은 스크롤에 묻히므로 `~/JOIN_CHAT.txt`에도 반드시 쓴다.
- `/j` 는 `t`를 검증하고 세션 쿠키를 심은 뒤 앱으로 리다이렉트한다.
- **폴백 경로 필수:** SSM 에이전트가 안 붙은 참가자는 반드시 1~2명 나온다.
  로그인 화면에 계정 ID + 공용 패스프레이즈(예: `woori-1030`, 슬라이드에 크게 표시) 수동 입력 경로를 남긴다.
  개인별 비밀번호 수동 입력은 500명 규모에서 관리 불가이므로 폴백은 **공용 패스프레이즈 1개**로 한다.
- 첫 로그인 시 계정 ID를 세션에 **sticky binding** 한다. 팀 실습이면 같은 계정 다중 세션을 허용하고 `...7391-2` 로 표시한다.
- 배포 산출물로 조인 URL의 **QR 코드 이미지**를 함께 생성한다(모바일 참가자용).

## 6. 기능 스펙

### 6.1 필수 (P0)

1. **채널** — 배포 시 `공지 / 질문 / 잡담` 자동 생성. 운영자만 채널 생성·아카이브 가능(참가자 생성 금지: 500명이면 난립).
   삭제 대신 **아카이브(읽기 전용)** — 엑셀 내보내기에서 누락되면 안 된다.
2. **스레드** — 플랫 채널은 60명이면 무너진다. 스레드는 P0다.
3. **질문 상태** — 각 질문에 `미해결 / 해결` 토글. 운영자 전용 **미해결 필터 뷰**.
4. **업보트** — 질문 정렬 및 중복 압력 해소용.
5. **코드블록 + 이미지 붙여넣기 업로드** — 실제로 올라오는 것은 대부분 에러 로그와 터미널 스크린샷이다. 클립보드 붙여넣기가 동작해야 한다.
6. **모바일 브라우저 정상 동작** — 사진은 폰으로 찍어 올린다.
7. **AI 챗** — Bedrock. 워크샵 랩 가이드를 컨텍스트로 사용(§6.3).
8. **랩 스텝 태깅** — 운영자 화면에 **현재 스텝 셀렉터** 1개. 이후 모든 질문/AI 쿼리에 `labStep` 자동 태깅.
   사후에 시각을 맞추는 것은 고통스럽고, 이건 거의 무료인데 값이 크다.
9. **엑셀 내보내기** (§8)
10. **운영자 모더레이션** — 메시지 삭제, 사용자 발언 차단. 익명 + 미디어 업로드 조합의 리스크 대비.

### 6.2 규모별 모드 (배포 파라미터 `--scale=small|large`)

| | small (~50명) | large (50명~) |
|---|---|---|
| 기본 뷰 | 채팅 타임라인 | **질문 목록(업보트 정렬)** |
| 잡담 채널 | 활성 | 비활성 또는 분리 |
| 운영자 뷰 | 스크롤 추적 | 미해결 필터 + 업보트 상위 |
| AI 챗 위치 | 보조 | **1차 방어선** (사람 답변 전) |

500명 플랫 채팅은 열자마자 무너진다. large 모드에서는 "채팅"이 아니라 "Q&A 보드"가 기본이다.

### 6.3 AI 챗 상세

- Bedrock Converse API. 모델 ID는 **배포 파라미터**(리전별 가용 모델이 다름). 미지원 리전 폴백을 명시.
- 랩 가이드/매뉴얼을 컨텍스트에 주입한다. 워크샵 특화 답변이 아니면 "Claude에 직접 물어보면 되는데?"가 되어 가치가 없다.
  - v1: 가이드 문서를 S3에 올려 프롬프트에 주입(파일 크기 상한 명시)
  - v2(선택): Bedrock Knowledge Base
- AI 답변은 채널을 오염시키지 않도록 **스레드 안 또는 질문자에게만** 표시한다.
- **사용자당 일일 토큰/요청 쿼터**를 둔다.
- 모든 AI 쿼리를 로깅한다. **이 로그가 산출물 중 가장 값지다** — 참가자가 가이드에서 못 찾은 것의 목록이다.
- 답변에 👍/👎 수집.

### 6.4 명시적 비목표 (하지 말 것)

- **비디오 트랜스코딩 금지.** MediaConvert를 넣는 순간 프로젝트 규모가 2배가 된다. mp4 50MB 상한으로 막는다.
- DM, 이모지 리액션 전체 세트, 음성/화상, 검색 고도화, 다국어 i18n — v1 범위 밖.
- 멀티 회차/멀티테넌시 — 1 배포 = 1 회차이므로 불필요.
- 미디어의 영구 보존 — 미디어는 계정과 함께 사라진다. 남길 값은 질문 텍스트에 있다.

## 7. 아키텍처

### 7.1 스택 (변경하려면 이유를 먼저 제시할 것)

```
CloudFront (+ WAF)
  ├── 정적 프런트 (S3)  … React + Vite
  └── /api, /j          … API Gateway → Lambda
실시간: AppSync Events (서버리스 pub/sub WebSocket)
인증:  Cognito User Pool (Central 계정에 배포)
데이터: DynamoDB 단일 테이블 (on-demand)
파일:  S3 presigned PUT
AI:    Bedrock (Lambda 경유)
poller: EventBridge Scheduler(2분) → Step Functions Map → Lambda
IaC:   AWS CDK (TypeScript), 원커맨드 배포
```

- 실시간은 **AppSync Events**를 1순위로 검토한다(실시간 코드량이 가장 적다). 부적합 판단 시 이유와 대안을 제시하고 승인받는다.
- 60~500 동접은 이 구성에서 비용·성능 모두 유의미하지 않은 수준이다. 과설계하지 말 것.

### 7.2 보안

- CloudFront + WAF(레이트 리밋). 메시지 크기 상한, 사용자별 초당 메시지 상한.
- `t` 파라미터는 3일짜리 팀 전용 자격증명이므로 URL 노출을 감수한다.
  다만 로그에 남지 않도록 리다이렉트 즉시 쿠키로 전환하고, 액세스 로그에서 쿼리스트링을 마스킹한다.
- 업로드는 확장자·MIME·크기 검증 후 presigned. 실행 가능 파일 차단.

## 8. 산출물: 엑셀 (이 앱의 유일한 영구 자산)

### 8.1 절대 규칙

- **내보내기는 이벤트가 아니라 상태다.** 15분마다(또는 쓰기 트리거) S3에 xlsx를 갱신해 "지금 시점 엑셀"이 항상 존재하게 한다.
- 운영자 화면 상단에 **항상** `지금 내보내기` 버튼 + `마지막 내보내기: HH:MM` 표시.
- README에 **굵게** 경고: 계정 소멸 전 다운로드하지 않으면 데이터는 사라진다.
- 데이터 모델은 이 엑셀 스키마의 투영으로 설계한다 → 변환 로직이 최소화된다.

### 8.2 시트 구성 (4장)

**Questions**

| ts | accountId | displayName | channel | threadId | body | status | resolvedAtMin | responder | upvotes | labStep |
|---|---|---|---|---|---|---|---|---|---|---|

**AI_Queries**

| ts | accountId | query | refDocs | answerSummary | feedback | labStep | tokensIn | tokensOut |
|---|---|---|---|---|---|---|---|---|

**Participants**

| accountId | displayName | questionCount | aiQueryCount | firstSeen | lastSeen | silent(무발화 여부) |
|---|---|---|---|---|---|---|

**Timeline**

| ts | accountId | event(login/upload/question/resolve/ai_query) | channel | refId | labStep |
|---|---|---|---|---|---|

### 8.3 미디어

- 기본: 미디어는 내보내지 않는다(계정과 함께 소멸).
- 옵션 플래그로 `zip(xlsx + media/)` 내보내기를 지원해도 된다. 단 P1.

## 9. 데이터 모델 (DynamoDB 단일 테이블)

먼저 §8.2 엑셀 스키마를 고정하고, 그 투영으로 키를 설계한다. 아래는 출발점이며 검토 후 확정한다.

| 엔티티 | PK | SK | 비고 |
|---|---|---|---|
| Channel | `CHANNEL#<slug>` | `META` | archived 플래그 |
| Message | `CHANNEL#<slug>` | `MSG#<ts>#<ulid>` | threadId, labStep 포함 |
| Thread reply | `THREAD#<threadId>` | `MSG#<ts>#<ulid>` | |
| Question index | `QSTATUS#<open\|resolved>` | `<ts>#<ulid>` | 운영자 미해결 필터용 |
| Participant | `USER#<accountId>` | `META` | 카운터 집계 |
| AI query | `USER#<accountId>` | `AI#<ts>#<ulid>` | |
| Timeline | `USER#<accountId>` | `EVT#<ts>#<ulid>` | |
| Lab step | `WORKSHOP` | `LABSTEP` | 현재 스텝 단일 아이템 |

- 업보트 정렬은 GSI 또는 주기 집계 중 선택. 500명 규모에서 강한 일관성은 불필요하다.
- TTL은 계정이 소멸하므로 불필요하지만 넣어도 무해하다.

## 10. 배포 인터페이스

```bash
npx cdk deploy \
  --context workshopName="woori-1030" \
  --context region="ap-northeast-2" \
  --context scale="large" \
  --context bedrockModelId="<model-id>" \
  --context operatorPasscode="<...>" \
  --context participantPassphrase="woori-1030" \
  --context joinMode="self|injected" \
  --context usernameSource="accountId|teamNumber"
```

**Outputs:** 앱 URL, QR 이미지 S3 URL, 운영자 콘솔 URL, 내보내기 S3 경로, poller 메트릭 링크.

- 하드코딩 0. 계정 ID, 리전, 도메인, 모델 ID, 워크샵명이 코드에 박혀 있으면 안 된다.
- `destroy` 절차와 비용 추정을 README에 명시한다.

## 11. 작업 순서 (이 순서로 진행)

1. **데이터 모델 확정** — §8.2 엑셀 스키마 ↔ §9 DynamoDB 키. 확정안을 문서로 먼저 제출하고 승인받는다.
2. **아키텍처 다이어그램** — `aws-diagram` 스킬 사용.
3. **CDK 스켈레톤** — 리소스 골격 + Outputs. 배포 성공 확인.
4. **인증·조인 경로** — poller, `/j`, 폴백 로그인. **여기가 최대 리스크이므로 먼저 검증한다.**
5. **채팅·스레드·질문 상태** — 핵심 기능.
6. **엑셀 내보내기** — 주기 스냅샷 포함.
7. **AI 챗** — 가이드 컨텍스트 주입.
8. **랩 스텝 태깅, 모더레이션, 규모별 모드.**
9. **부하 테스트** — 최소 60 동접, 가능하면 500 시뮬레이션.
10. **README / 운영자 런북.**

각 단계 끝에서 무엇을 만들었고 다음에 무엇을 할지 3줄 요약을 남긴다.

## 12. 작업 규칙

1. **추측 금지.** 스펙에 없는 결정이 필요하면 진행을 멈추고 질문한다. 특히: 실시간 방식 변경, 스택 교체, 새 AWS 서비스 도입, 비목표(§6.4) 위반.
2. **§3의 제약은 협상 불가.** 상주 인프라를 전제하는 제안, 리전 하드코딩, 실명/이메일 수집은 즉시 거부한다.
3. **작게 커밋한다.** 단계별로 동작하는 상태를 유지한다.
4. **폴백 없는 경로를 만들지 않는다.** 특히 참여 경로. 워크샵 커뮤니케이션 생명줄을 v1 앱 하나에 전부 걸면 안 된다. README에 예비 Slack/Discord 링크 QR을 인쇄해두라고 명시한다.
5. **운영자 화면은 "지금 막힌 사람이 누구인가"에 최적화한다.** 예쁜 UI보다 미해결 목록이 우선이다.
6. **다른 SA가 쓸 배포물이다.** 오준석 개인 환경 가정 금지. README만 읽고 배포 가능해야 한다.
7. **테스트:** 데이터 모델 → 엑셀 변환, poller 멱등성, 토큰 검증은 유닛 테스트를 반드시 작성한다.
8. **Bedrock 모델 ID·Cognito 쿼터·AppSync Events 사양은 최신 문서를 확인하고 쓴다.** 기억에 의존하지 말 것.
